# Operating the PM tree

Milestone → feature → story, as markdown with YAML frontmatter under `pm/roadmap/`. Bugs hang off
a milestone. The id is in the FRONTMATTER and never in the path, so a grain is movable,
renameable and re-parentable without breaking a reference to it. The tree is packed context: it
holds the work, its state and its record, and it infers nothing.

## The tree records what it cost, and `pm ledger` reads it back

**Before hand-writing a table of timings, token counts or grain durations: the tree already has
them.** Every status flip, decision and `--force` files a row; a `Stop`/`SubagentStop` hook sums
each session's transcript into one; every gate run files what it cost.

    pm ledger show <grain-id>       that grain's rows oldest first, with the
                                    seconds between status changes
    pm ledger report [<grain-id>]   the units of work a milestone OWNS, then
                                    spend by agent and time per state
    pm ledger report --tree         the rows no milestone owns: gate cost
    pm ledger report <a> <b>        TWO OR MORE MILESTONES SIDE BY SIDE, each
                                    block with a `delta` row

`--json` gives the same numbers to a script; `--from <rev>` reads a retired milestone out of git.
A row naming a grain lives in its milestone's ledger; a row naming none lives in
`<roadmap>/ledger.jsonl`. What a run on this machine cost (`gate`, `test`, `verify` rows) lands in
the gitignored `<roadmap>/ledger.local.jsonl`. Both read verbs read every file. A number a row
cannot hold does not belong in the tree.

## The grains

```
pm/roadmap/
  releases.md                    the plan — `order`, one MILESTONE ID per line
  milestones/<slug>.md           id, kind, name, status, + your project's own fields
  milestones/<stem>-handoff.md   cold-start only — never what `pm status` computes
  milestones/<stem>-decisions.md DURABLE, append-only; survives close
  features/<slug>.md             milestone: <milestone-id>   ← its binding
  stories/<slug>.md              feature: <feature-id>
  bugs/<slug>.md                 milestone: <milestone-id>   ← its parent (which one: `bugs bind:`)
  ledgers/<milestone-id>.jsonl   that milestone's rows
  ledger.jsonl                   rows naming no grain
  ledger.local.jsonl             gate/test/verify cost — gitignored, this machine's
```

**One flat pool per kind.** `id:` is what every reader keys on, `kind:` says what it is, and the
binding field (`milestone:` on a feature or bug, `feature:` on a story) says what it belongs to.
**The filename is yours**: nothing reads a path as schema. Re-parenting is one line, `pm set <id>
feature <fid>`. A grain with no binding is UNBOUND, a census line and not an error; a binding
naming a grain not in the tree is a V7 finding.

**Scaffold, never hand-create.** `pm new milestone|feature|story|bug` renders each grain from a
template at its initial status. The name is the LAST words of every create (`pm new bug
<milestone> <slug> <name...>`); a name led by `-` or holding a newline is refused at exit 2.
`new milestone` and `new feature` are idempotent and fill missing slots. `decisions.md` appears
when `pm decide <grain-id> <title>` records the first decision; the reasoning under the heading is
yours. `pm rename <old> <new>` corrects an id. `pm templates` copies the templates out for
`[pm] template_dir`. `[pm.required.story] lines = ["Destination:"]` makes `pm new` write a line
and `check pm` WARN while it is empty.

## Status vocabularies

Declared in `devkit.toml` under `[pm.states.<kind>]`, written by `pm init`. Every state sits in
exactly one CATEGORY — `todo`, `in_progress`, `done` — and every question the tool asks is asked
of the category. Any declared state is reachable directly. `pm vocabulary --json` prints the
declaration and the rule ids `[pm] checks` may name; read it after a pin bump. The seed:

| Grain | `todo` | `in_progress` | `done` |
|---|---|---|---|
| Milestone | `planning` `ready` | `building` `reviewing` `accepted` `packaging` | `done` `obe` |
| Feature | `planning` `ready` | `building` `reviewing` | `done` `obe` |
| Story | `planning` `ready` | `building` | `done` `obe` |
| Bug | `open` | `fixed` | `closed` |

`done` does not mean SHIPPED. It means everything inside the tree's authority is finished; `obe`
sits beside it because abandoned work is finished too. Branch, PR, merge and tag are git events
after `done`. A status the project never declared is a `check pm` D4 finding.

## Decomposing work

- **A feature earns its slot** by being a coherent, shippable piece. If you cannot state what it
  makes true, it is not a feature.
- **A story is one builder's brief**: the observation it makes true, the files it touches, the
  proof and its tier, and what other lanes own. Cut what the builder can derive.
- **Stories are observations, not tasks.** "The save slot card shows the lineage name", not
  "implement SaveSlotCard.set_name()".
- **Dependencies go in frontmatter**, never in prose: `depends_on`, `consumed_by`. `pm validate`
  checks they resolve.
- **Cite `file::symbol`, never a line number.** Lines move under concurrent edits.

## Sequence — `order:` on the parent, written by `pm add`

`make pm ARGS='add <parent-id> <child-id>'` binds the child and places it in one act;
`--position N`, `--before <id>` or `--after <id>` says where. `pm remove` is the pair. `pm status`
reads that order; anything unsequenced prints after it. The list is OPTIONAL. `pm next` names the
first entry in `releases.md` that has not shipped.

## Reading the tools

- **`pm status [<milestone>]`** — the whole tree, with `<DRIFT: …>` and `<WARN: …>` marks off the
  same predicates the gate reports on. Never hand-copy a tally out of it.
- **`pm list [--status …] [--owner …] [--milestone …] [--json]`** — one tab-separated
  `<id>  <status>  <owner>  <feature>  <name>` per story; `--kind milestone` gives
  `<id>  <status>  <category>  <branch>  <name>`. **Read verbs emit LINES**: `pm list | grep` is
  the search, and a thing you cannot pipe is a missing COLUMN, never a new verb.
- **`pm validate`** — well-formed frontmatter, bindings of the right kind, refs that resolve, an
  acyclic graph. **UNVERIFIABLE** is not a failure: it counts refs into retired milestones.
- **`check pm`** — the same rules plus status drift, as a gate. Fix a failure with the CLI, never a
  `status:` edit. A `  WARN  ` line moves nothing: an `in_progress` grain with an empty section, a
  parent and child that disagree. A `done` parent over a child that is not is D11, a FAIL.

## Retiring a closed milestone — git history is the archive

`pm retire <milestone-id> [<why>]` deletes the grains a milestone owns: its document, every
feature and bug bound to it, their stories, the shared docs beside each, and its ledger.
`--dry-run` writes nothing. Do it in a commit of its own: that commit is the resurrect anchor
(`git show <hash>:<old-path>`). Ids stay canonical forever; a ref naming a retired one is
UNVERIFIABLE. A `retire` row in `ledger.jsonl` keeps the version, name and why, which
`pm roadmap` prints. A milestone pruned before that row existed gets one with `pm retire <id>
--version <ver> --name <name> [<why>]`.
