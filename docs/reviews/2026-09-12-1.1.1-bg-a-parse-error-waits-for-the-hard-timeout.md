# 1.1.1 — bg-a-parse-error-waits-for-the-hard-timeout: lane review (GitHub #12)

Reviewer run 2026-09-12 over `020a362^1..020a362` (lane commit `ca0faf7`, merge `020a362`). Method:
I read the diff end to end, plus `scenario.sh`'s run and verdict section and `integration.sh`'s
fan-out. I then ran 20 probes in a scratch project, at stock layout, under `/bin/bash` 3.2.57 with
the REAL GNU `timeout` (`/opt/homebrew/bin/timeout`), old (`020a362^1`) against new (`020a362`).
I also ran `tests/test_runners_installable.py`: 25 passed at the merge head (my run). The new case
fails against the pre-fix installables (30.9s, my run). `scenario.sh --self-test` (20) and
`gdk_runners.sh --self-test` (51) are OK, and `shellcheck -x` on both is clean.

**Verdict: SHIP-WITH-FIXES.** For an engine that IS the pid it was exec'd as, the fix does what the
brief asks. Signature then `exec sleep` gives exit 1 in 0.49s, and the message names the line. The
Godot 4 `ERROR: res://…:3 - Parse Error:` shape takes 0.36s. A TERM-ignoring engine is escalated
to SIGKILL (2.54s with `GDK_TIMEOUT_KILL_AFTER=2s`). A signature the allowlist admits does not stop
the run: PASS exits 0, and a hang still reports `(likely hang)` with exit 3. With the watch
neutralised in a scratch copy, the backstop reads `HARD_TIMEOUT — exceeded 2s, killed (GDScript
parse error: …)`, exit 3. Cold/stale recovery with a real `timeout` does 3 boots and exits 0. No
probe left a stray process or a tmp file.

The fix only stops the single pid, though, and that is M1. For an engine that forks rather than
execs, the run no longer has a bound at all.

## Blockers

- `M1` MAJOR `src/godot_devkit/godot/installables/scenario.sh:502` (+ `gdk_runners.sh:382`): the
  watch TERMs the pid the shim exec'd, and nothing else. When `GDK_GODOT` forks its engine (a
  wrapper script without `exec`, `flatpak run`, a version shim), that pid is only the wrapper.
  The wrapper dies, and GNU `timeout` sees its child exit and exits too, WITHOUT signalling the
  process group it set up. The engine, now orphaned, keeps the pipe open, and the pipeline waits
  on it.
  **Repro:** stub `godot` = `echo 'SCRIPT ERROR: Parse Error: …' >&2; sleep 32` (no `exec`), with
  `GDK_SCENARIO_HARD_TIMEOUT=5`. Pre-fix: exit 3 after 5.2s. Merge head: exit 1 after 32.4s. With
  a child that never quits (the brief's own condition), the run never returns. That is worse than
  the bug. Ctrl-C also misses the orphan, because it sits in `timeout`'s group, not the terminal's.
  The lane's test hides this by using `exec sleep 30`. The same test without `exec` fails at the
  merge head (30.7s, my run).
  **Fix:** stop the BOUND, not the engine. TERM the `timeout` pid itself (put the shim in front of
  `$GDK_TIMEOUT`). GNU timeout's handler already forwards the signal to the whole group and
  applies its own `--kill-after`. `gdk_stop_bounded`'s escalation loop is then a copy of what
  `timeout` does, and it can go. That is the smaller end state, and it removes a new public
  library function from a patch (Q3). Amend the lane's case to drop `exec`. No new test.

Also noted:
- `m2` MINOR `scenario.sh:72`: `Parse Error:` is unanchored. The same file's comment at `:62-64`
  says that is exactly what ENGINE_ERROR_PATTERN must not be. A runner log line like `[info] saw
  JSON Parse Error: expected, handled` followed by PASS now gives FAIL exit 1 when the engine
  lives past one 0.2s poll, and PASS exit 0 when it exits sooner (3/3 PASS at 0.35s). Pre-fix it
  was PASS every time. So the verdict on the same input depends on timing. It is a loud false
  FAIL that names its line, which is why it is MINOR and not MAJOR. **Fix:**
  `^(SCRIPT ERROR: Parse Error|ERROR: .* - Parse Error:)`. It also labels VariantParser's
  `.tscn`/`.tres` `Parse Error:` as "GDScript".
- `Q3` QUESTION, rule 7: this class's exit code moves from 3 to 1. It gains a new verdict line, and
  the library gains a new public function (`gdk_stop_bounded`), all in a patch, as the brief
  specifies. The exit set and the `[SCENARIO] <name> FAIL — …` family are unchanged, and
  `HARD_TIMEOUT — exceeded Ns, killed (` keeps its prefix. A consumer that greps `likely hang`
  misses only the backstop variant. Patch or minor is the operator's call. If M1's fix deletes
  `gdk_stop_bounded`, only the line is left to decide.
- `N4` NIT `scenario.sh:482`: "pass the live stream through untouched" is not exact. awk adds a
  newline to an unterminated last line (70164 → 70165 bytes). BSD awk 20200816 also drops the
  rest of a line after a NUL (`x\0y` → `x`, 43 → 41 bytes). Stdout was byte-identical in both
  cases. State this in the comment.
- `N5` NIT `scenario.sh:496-505`: the poll forks grep/head/sleep five times a second. A 10s
  scenario goes from 0.07 to 0.53 CPU-s user+sys (0.69 with an allowlist), and that lands in
  `integration.sh`'s boots CPU line. A builtin `[ -s "$hits" ] ||` guard before the grep removes
  almost all of it.
- `N6` NIT `scenario.sh:603-608`: the verdict wording is also timing-dependent. A parse error
  followed by a quick exit reports `FAIL — engine-level errors…` (0.37s); one that lingers past a
  poll reports `FAIL — GDScript parse error:` (0.87s). Both exit 1. Falling back to
  `parse_error_line "$RUN_REPORT"` after every run, when the marker is empty, would make it
  deterministic, and the separate hang-branch backstop would fold into it.
- `N7` NIT `tests/test_runners_installable.py:420,426`: `TIMEOUT_STUB` is a pass-through, so
  `GDK_SCENARIO_HARD_TIMEOUT='20'` does nothing and "outlives the bound" overstates what the case
  shows. The case proves the watch, not how it interacts with a real bound, which is where M1
  lives. M1's amendment (no `exec`) closes the gap.
- `N8` NIT `gdk_runners.sh:382-384`: a grace such as `500ms` or `1m`, both valid for GNU timeout,
  silently becomes 5s. The SIGKILL escalation has no case in the library self-test; only my probe
  exercised it. Both go away with M1's fix.
